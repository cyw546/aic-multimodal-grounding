## 1. 目标、边界与最终交付

### 1.1 目标

在新服务器上恢复 GroundingDINO Swin-B RGB 基线，使用真实复赛数据完成小批量推理和固定 100 条查询的四组阈值实验，最终给出可复现的 V1 推荐参数。

### 1.2 服务器路径

- 代码目录：`/srv/nfs/home/njnu_lhf/aic-repechage/project`
- 数据目录：`/srv/nfs/data/aic-repechage/official/repechage`
- 建议开发分支：`feature/repechage-rgb-baseline`

### 1.3 最终交付

- GroundingDINO 来源、提交版本、安装命令和配置路径。
- Swin-B 权重来源、保存位置、文件大小和 SHA-256。
- 至少 10 条真实复赛查询的合法预测结果。
- 固定 100 条查询的四组阈值实验。
- 每组成功数、首次无候选数、降阈值恢复数、默认框数、平均分和耗时。
- 至少 20 条预测可视化及人工检查结论。
- 明确的 V1 推荐阈值和选择理由。
- `docs/repechage_rgb_baseline.md`、通用配置、实验脚本和相应测试。

### 1.4 明确禁止

- 正式提交 JSON 不额外加入 `score` 等诊断字段；诊断信息写入独立的实验 JSONL/JSON。

## 2. 总体责任划分

由于校园网与 Codex 不能同时访问，本项目采用“Codex 本地准备执行包—你切到校园网批量执行—带回结果包”的离线交接模式。你负责的事项尽量压缩为：

1. 每轮从 Codex 侧取得一个已经准备好的服务器执行包。
2. 切换到校园网，在服务器上运行执行包中的唯一入口命令。
3. 把执行包产生的小型结果包带回 Codex 侧。
4. 对安装依赖、下载权重等写操作进行授权。
5. 确认我们使用的 100 条查询确实符合团队约定。
6. 最终快速检查可视化和 V1 推荐结论。
7. 决定是否提交 commit、推送分支和创建 PR。

Codex 负责：

1. 在本地仓库中准备每轮唯一入口脚本、说明和预期输出，不让你在服务器临时拼接命令。
2. 让脚本自动检查服务器、仓库、GPU、数据、源码、配置和权重，并把信息写入小型结果包。
3. 设计并实现实验脚本、统计、断点续跑和可视化。
4. 根据你带回的日志和结果包分析问题，生成下一轮执行包。
5. 分析最终结果、定位异常、整理 V1 推荐参数。
6. 编写文档、测试和复现命令。
7. 每一步报告证据，不把“命令执行完成”误认为“任务验收通过”。

离线协作的核心规则：服务器侧不需要运行 Codex；服务器只运行已经审阅过的确定性 shell/Python 脚本。脚本不能读取或输出令牌、私钥、完整环境变量，也不能自动提交或推送 Git。

## 3. 阶段 0：建立离线双端交接流程

当前 Codex 任务运行在 Windows 本地目录 `D:\Code\codex_aic`，无法与只能通过校园网访问的服务器保持实时连接。因此不再把“Codex 直接运行在服务器目录”作为前提，而是通过三轮离线执行包完成工作；正常情况下只需要两次服务器执行，第三次仅用于补跑或最终验证。

### 3.1 每轮执行包的固定结构

Codex 在仓库中准备：

```text
server_packets/
└── round_N_<purpose>/
    ├── README.md             # 本轮只需要阅读这一页
    ├── run.sh                # 本轮唯一入口
    ├── scripts/              # run.sh 调用的辅助脚本
    ├── expected_outputs.txt  # 应生成的文件清单
    └── SHA256SUMS            # 执行包自身校验值
```

服务器执行后，只把下面的小型目录带回：

```text
server_results/
└── round_N_<purpose>/
    ├── STATUS.txt            # PASS、FAIL 或 INCOMPLETE
    ├── summary.json          # 机器可读摘要
    ├── commands.log          # 实际执行的非敏感命令
    ├── stdout.log
    ├── stderr.log
    ├── git_status.txt
    └── checksums.txt
```

结果包不得包含图片数据集、权重、私钥、令牌、完整 `env` 输出或大型预测文件。需要查看的 20 张可视化可以单独压缩带回，预计体积远小于模型和数据。

### 3.2 第一次服务器往返：只读资产采集

Codex 先准备 `round_1_audit`。你切换到校园网后只执行：

```bash
cd /srv/nfs/home/njnu_lhf/aic-repechage/project
bash server_packets/round_1_audit/run.sh
```

该脚本必须是只读的，自动记录：

- 主机名、Linux 版本、当前目录和时间。
- Git 根目录、remote、分支、HEAD 和工作树状态。
- 数据目录是否可读、候选 JSON 文件、文件数量和少量结构摘要。
- GPU、驱动、CUDA、Python、PyTorch 和 torchvision 信息。
- GroundingDINO 源码、配置和候选权重的位置。
- 权重大小及 SHA-256，但不复制权重。
- 可用磁盘空间以及建议输出目录是否可写。

执行结束后，你只需确认终端最后显示结果包路径，然后把整个 `server_results/round_1_audit/` 带回本机交给 Codex。

### 3.3 Codex 侧离线分析

你恢复 Codex 网络后，把第一轮结果包放进当前工作区或直接附加。Codex 将：

1. 检查 `STATUS.txt`、日志和校验值。
2. 输出 READY/MISSING/INCOMPATIBLE/UNKNOWN 资产表。
3. 根据真实服务器状态一次性准备环境恢复、冒烟测试和实验工具。
4. 如果第一轮信息足够，直接生成第二轮“一键执行包”，不要求你先回服务器补充零散命令。

只有第一轮结果包信息不足且无法安全推断时，才安排补充采集；补充项会合并成一个新脚本，避免多次来回询问。

### 3.4 第二次服务器往返：恢复、冒烟和正式实验

第二轮执行包应支持分阶段和断点续跑，但仍只有一个入口：

```bash

```

`run.sh` 自动按顺序完成：


任何阶段失败时，脚本立即停止后续阶段，保存 checkpoint、失败阶段、完整错误日志和可恢复命令。你不需要在服务器现场调试；把结果包带回即可。

## 7. 阶段 4：确认真实数据和单样本接口

## 9. 阶段 6：实现并验证正式实验工具

这一阶段发生在本地 Codex 侧，时间上位于第一轮审计结果分析之后、第二次校园网切换之前。工具必须提前准备好，不能等服务器冒烟测试结束后再临时开发。

## 10. 阶段 7：运行固定 100 条、四组阈值实验

  - 样本总数。
  - 合法输出数。
  - 主阈值成功数。
  - 首次无候选数。
  - 降阈值恢复数。
  - 默认框数。
  - 平均分和中位分。
  - 总耗时和平均单条耗时。
- 对每组正式 JSON 运行现有校验器。

### 你需要做什么

- 建议在 `tmux` 中启动第二轮入口脚本，等待它输出最终状态和结果包路径。

### 阶段 7 通过标准

- 四组均完成相同的 100 条查询。
- 每组 JSON 校验通过。
- 汇总数字与明细记录数量一致。
- 失败、回退和默认框均可以追溯到具体 Query ID。

只有四组数据完整，才进入阶段 8。

- 至少 20 条已经人工检查。
- 推荐参数明确到 `box_threshold` 和 `text_threshold`。
- 推荐结论没有把模型 score 错当成真实准确率。
- 结论同时考虑覆盖率、回退率、可视化质量和耗时。

只有推荐得到确认，才进入阶段 9。

## 12. 阶段 9：文档、清理与提交决策

### Codex 做什么

- 完成 `docs/repechage_rgb_baseline.md`。

- 运行完整测试和 `scripts/check_repo_safety.py`。
- 检查 Git diff，确认没有数据、权重、预测、日志或凭据。
- 向你展示待提交文件和变更摘要。

### 你需要做什么

- 审阅最终文档和变更。
- 明确决定以下三项：
  1. 是否创建 commit。
  2. 是否推送分支。
  3. 是否创建 Pull Request。

### 阶段 9 通过标准

- 验收标准全部满足。
- 安全检查和测试通过。
- 只有得到明确授权后，Codex 才执行 commit、push 或创建 PR。

## 14. 你现在只需要做的第一件事

暂时不要切换到校园网，也不要在服务器临时执行检查命令。先让 Codex 在本地准备并检查 `round_1_audit` 执行包。执行包准备完成后，Codex 会明确告诉你：

- 预计运行时间。
